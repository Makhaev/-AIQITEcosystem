## Что работает

- Dashboard («Обзор»): шесть показателей для администратора и руководителя, московские сутки, посещаемость по всем отметкам с общей формулой Student 360, выбор периода и просроченные задачи. [Контракт и правила](docs/dashboard.md).
- Audit Log («История действий»): критические изменения и названия изменённых полей в одной транзакции, фильтры и пагинация, доступ только администратору, запрет изменения/удаления и отсутствие секретов и контактных значений. [Контракт и правила](docs/audit-log.md).
- Вход по email и паролю, выход, смена собственного пароля.
- Создание пользователей администратором, список с пагинацией, изменение имени и ролей, блокировка, разблокировка и сброс пароля.
- Педагоги: создание и редактирование администратором, профиль, поиск по ФИО без учёта регистра, пагинация, фильтр по статусу, архивирование и восстановление, необязательная уникальная связь с учётной записью. Руководитель читает все профили; педагог — только собственный, включая проверку по ID.
- Ученики и родители: карточки, поиск, пагинация, редактирование, архив и восстановление. Необязательная дата рождения и куратор; у родителя обязателен телефон или email. Форма предупреждает о совпадении контактов, включая архив, и позволяет явно сохранить отдельного человека; после ошибки проверки доступен повтор. Связи многие-ко-многим содержат представительство и основной контакт; повторные пары и второй основной контакт запрещены в PostgreSQL. Куратор читает только закреплённых учеников и их родителей, включая фильтрацию детей в общей карточке родителя. [Контракт и правила](docs/students-and-parents.md).
- Программы: название, описание, статусы draft/active/archived, поиск, пагинация, редактирование и архив. Модули: создание/изменение, уникальные номера внутри программы и упорядоченный список. Новая связь группы требует активной программы; составные FK запрещают занятие с модулем другой программы. [Контракт, права и ограничения](docs/programs-and-modules.md).
- Группы: создание, редактирование, карточка и архив; зачисление и вывод с датами и сохранением истории. PostgreSQL запрещает повторное активное зачисление и переполнение при параллельных запросах; перевод выполняется в транзакции и сохраняет посещаемость. [Контракт и ограничения](docs/groups-and-enrollments.md).
- Расписание: занятия, необязательный модуль, статусы, московское время и фильтры. Ограничения PostgreSQL запрещают пересечения группы или педагога, включая параллельные запросы; отменённые занятия не занимают интервал. Состав журнала фиксируется на дату занятия при первом открытии; администратор исправляет его с причиной и audit, сохраняя прежние отметки. [Расписание и журнал](docs/lessons-and-journals.md).
- Посещаемость: пять статусов, комментарий до 500 символов, повторное и атомарное массовое сохранение, «Все присутствовали». Педагог отмечает и завершает только свои занятия; завершение — после окончания и без unmarked, отмена с внесёнными отметками запрещена. Исправление завершённого журнала доступно администратору. [Посещаемость и переходы статусов](docs/attendance.md).
- Общая матрица прав с запретом по умолчанию и объектными ограничениями: [роли и педагоги](docs/roles-and-teachers.md).
- Задачи: администратор и руководитель создают, назначают и редактируют задачи; педагог и куратор видят свои и меняют допустимые статусы. Поиск, сроки, фильтр просроченных, необязательная связь с учеником, группой или занятием. Назначение проверяет доступ ответственного в транзакции; после отзыва доступа задача остаётся, а сведения об объекте и ссылка скрываются, в том числе в открытой карточке. [Проверки R02](docs/completion-progress.md).
- Роли `admin`, `leader`, `teacher`, `curator`, `methodologist`, `education_leader`. Управление пользователями доступно только `admin`. Права подготовки и публикации версий разделены и проверяются сервером.
- Уникальный email без учёта регистра; bcrypt с cost 10. Пароли — минимум 12 Unicode-символов, максимум 72 байта UTF-8.
- Сессии на 12 часов в PostgreSQL. Случайные токены по 256 бит; в БД сохраняются SHA-256 хеши. В браузере — host-only `HttpOnly`, `SameSite=Strict` cookies; `Secure` включается при HTTPS в `APP_ORIGIN`.
- CSRF для всех изменяющих запросов, включая вход: точная проверка `Origin`, cookie и `X-CSRF-Token`; после входа токен дополнительно привязан к серверной сессии.
- Выход отзывает текущую сессию; смена/сброс пароля, блокировка и изменение ролей отзывают все сессии пользователя.
- Создание и изменение пользователей повторно проверяют сессию и права администратора внутри транзакции. Истечение сессии во время ожидания блокировки также прекращает доступ.
- Временные пароли необходимо сменить при входе. До смены доступны только `/auth/me`, `/auth/logout`, `/auth/change-password` и получение CSRF-токена.
- Защита последнего активного администратора, ограничение попыток входа, базовый audit авторизации и изменений пользователей.
- `/health/live`, `/health/ready`, миграции при запуске, структурированные логи без тел запросов и секретов.

Публичной регистрации и почтового восстановления пароля нет. Ученики и родители не имеют собственных кабинетов. Для расписания требуется расширение PostgreSQL `btree_gist`, устанавливаемое миграцией `006_lessons.sql`. Общая тема и компоненты соответствуют брендбуку AIQ: [дизайн-система и проверки](docs/frontend/design-system.md). Интерфейс проверяется на desktop и ширине 360 px. При запуске учебные демонстрационные записи не создаются; тестовые данные и снимки интерфейса вымышлены.

## Запуск через Docker Compose

Нужен Docker с Compose. Из корня проекта:

```powershell
Copy-Item .env.example .env
```

В `.env` замените `POSTGRES_PASSWORD` случайным паролем из букв и цифр (он используется в URL подключения). `APP_ORIGIN` должен точно совпадать с адресом браузера, включая порт; `localhost` и `127.0.0.1` — разные origins.

```powershell
docker compose up --build -d
```

Откройте `http://localhost:8080`. Перед первым входом создайте администратора отдельной командой.

Для публичного HTTPS используйте [инструкцию пилота R11](docs/operations.md#https-пилот-r11) и самостоятельный `compose.pilot.yaml`. Автоматическая проверка пустого Docker/HTTPS-стенда: `node scripts/verify-r11.mjs` (Docker Engine/Compose и Node 22.12+). Фактические результаты и ограничения окружения: [отчёт R11](docs/r11-operations-report.md).

## Первый администратор

Команда создаёт первого администратора только в пустой системе и не меняет существующие аккаунты. Пароля по умолчанию нет. Для PowerShell пароль вводится скрыто и не попадает в историю команд:

```powershell
$env:ADMIN_EMAIL = 'admin@example.test'
$env:ADMIN_NAME = 'Администратор AIQ'
$adminSecure = Read-Host 'Пароль администратора (минимум 12 символов)' -AsSecureString
$adminPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($adminSecure)
try {
    $env:ADMIN_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($adminPointer)
    docker compose run --rm -e ADMIN_EMAIL -e ADMIN_NAME -e ADMIN_PASSWORD admin
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($adminPointer)
    Remove-Item Env:ADMIN_PASSWORD -ErrorAction SilentlyContinue
    Remove-Item Env:ADMIN_EMAIL -ErrorAction SilentlyContinue
    Remove-Item Env:ADMIN_NAME -ErrorAction SilentlyContinue
}
```

Для запуска backend вне Docker используется та же команда `go run ./cmd/admin` из папки `backend`, с установленной `DATABASE_URL`. Замените только строку `docker compose run …` в приведённом примере.

## Миграции БД

SQL-файлы `backend/migrations/001_*.sql`…`016_*.sql` встроены в бинарники. Сервер и команда администратора автоматически применяют новые миграции перед работой. Миграция 016 разделяет `lesson_participants` и `attendance`, сохраняя ID и историю; она требует новой версии backend. Перед обновлением делают копию БД и останавливают старые экземпляры приложения. Подробности: [схема и миграция](docs/database-schema.md). Для отдельного запуска:

```powershell
docker compose run --rm --build migrate
```

Без Docker, из `backend`, с установленной `DATABASE_URL`:

```powershell
go run ./cmd/migrate
```

Миграции применяются по имени, один раз, в транзакции с advisory lock; версии фиксируются в `schema_migrations`. Повторный запуск безопасен. Пользователю БД нужны права DDL и установки `btree_gist`. Уже применённые файлы не редактируют: добавляют следующий номер. Обратных миграций нет; перед обновлением делают резервную копию. Учебные карточки архивируются, история зачислений и посещаемости сохраняется; каскадного удаления учебной истории нет.

## Резервное копирование и восстановление

R12 реализован отдельным процессом `backup serve`: ежедневный `pg_dump -Fc` в
**03:00 Europe/Moscow**, семь последних успешных копий. До публикации временный
архив полностью читается через `pg_restore`, проверяются SHA-256 и размер.
Ротация начинается после успешного сохранения; сбой сохраняет прежние архивы
и даёт `failed`/ненулевой код `backup status` и Docker `unhealthy`.

Подготовьте отдельное шифрованное хранилище с правами владельца `0700` (Windows:
закрытый ACL), маркером `.aiq-backup-store`, отдельный каталог статуса и роль
БД только для чтения. Параметры: `BACKUP_DATABASE_URL`, `BACKUP_STORE_HOST`,
`BACKUP_STATE_HOST`, `BACKUP_TIME=03:00`. Подключение для обычного Compose:

`docker compose -f compose.yaml -f compose.backup.yaml up -d --build backup`

Для HTTPS-пилота используйте `compose.pilot.yaml`, `compose.backup.yaml` и
`compose.backup-pilot.yaml`. Без Docker доступен systemd unit.
Оператор проверяет код `backup status`, возраст копии (не более 26 часов) и
журнал службы; при ошибке устраняет проблему БД/хранилища/прав и повторяет запуск
без удаления старых копий. Внешние уведомления подключаются в согласованном
окружении эксплуатации.

`backup restore ID` создаёт новую случайно названную БД, проверяет миграции,
количества и хеши всех строк. Рабочая БД не перезаписывается. Приёмка дополнительно
проверяет вход и учебные данные через приложение, расписание, ротацию и отказы.

Полные команды, права, параметры, действия при сбоях и восстановление:
[инструкция R12](docs/backup-r12.md). Результаты и границы подтверждения:
[отчёт R12](docs/r12-backup-report.md).

## Разработка без контейнеров приложения

Требуются Go 1.24+ и PostgreSQL 17. Для frontend рекомендуется Node.js 22.12+. В dev-зависимостях закреплён локальный Node.js 22, который используется npm-скриптами. На Windows добавлена явная optional-зависимость нативного сборщика Vite; на Linux npm её пропускает.

Можно поднять только БД: `docker compose up -d db`. В терминале backend:

```powershell
$env:DATABASE_URL = 'postgres://aiq:YOUR_DB_PASSWORD@127.0.0.1:5432/aiq?sslmode=disable'
$env:APP_ORIGIN = 'http://localhost:5173'
Set-Location backend
go mod download
go run ./cmd/server
```

В отдельном терминале из корня:

```powershell
Set-Location frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173`. Vite проксирует `/api` и `/health` к Go на порту 8080. Backend не загружает `.env` автоматически: вне Compose переменные задаются в окружении.

Для HTTPS укажите `APP_ORIGIN=https://ваш-домен` и настройте TLS на внешнем reverse proxy. В Compose `TRUST_PROXY=true`, поскольку backend не опубликован на хосте и принимает запросы через nginx. Nginx заменяет `X-Real-IP` адресом клиента для ограничения входов. При прямом доступе к backend оставьте `TRUST_PROXY=false`; включайте доверие только для backend, доступного исключительно через контролируемый proxy.

| POST | `/lessons/{id}/snapshot` | Исправление исторического снимка, только admin |
| GET | `/lessons/{id}/snapshot-history` | Предыдущие версии снимка, только admin |
| GET, POST | `/tasks` | Список и создание задач |
| GET | `/tasks/assignees` | Список допустимых исполнителей |
| GET, PATCH | `/tasks/{id}` | Карточка и редактирование задачи |
| PATCH | `/tasks/{id}/status` | Изменение статуса с проверкой прав |
| GET | `/dashboard` | Показатели для admin/leader |
| GET | `/audit-logs`, `/audit-logs/{id}` | Журнал только для admin, только чтение |

API-клиент сохраняет cookies из `/auth/csrf`, передаёт `Origin: APP_ORIGIN` и `X-CSRF-Token` при POST/PATCH/PUT/DELETE. После входа используется новый `csrf_token` из ответа. Сессионный токен передаётся только через cookie. Ошибка содержит `code`, `message`, `field_errors`, `request_id`. Изменение email текущим API не предусмотрено.

Списки возвращают `items`, `total`, `page`, `page_size`; по умолчанию `page=1`, `page_size=20`, максимум 100. Неверные значения дают `400`, а страница за пределами списка — пустой `items` с общим `total`. Сортировка заканчивается уникальным ID. Вложенные массивы карточек и состав одного журнала являются полным снимком, а не отдельной страницей списка. Health endpoints находятся вне префикса API: `/health/live` проверяет процесс, `/health/ready` — соединение с БД.

## Проверки

```powershell
Set-Location backend
go test ./...
go vet ./...
go build ./cmd/server ./cmd/admin ./cmd/migrate
```

Для интеграционных тестов задайте `TEST_DATABASE_URL` к тестовой БД. Каждый тест создаёт отдельную схему `aiq_test_*` и удаляет только её после проверки. Пользователю БД нужны права создания схем. Без переменной интеграционные тесты явно пропускаются; в CI переменная обязательна и настроена.

```powershell
$env:TEST_DATABASE_URL = 'postgres://aiq:YOUR_DB_PASSWORD@127.0.0.1:5432/aiq_test?sslmode=disable'
go test -count=1 ./...
```

Сборка frontend:

```powershell
Set-Location frontend
npm ci
npm run build
```

Браузерные проверки для desktop и 360 px:

```powershell
npx playwright install chromium
npm run test:ui
```

CI проверяет интеграцию с PostgreSQL, `go test -race`, `go vet`, сборку Go/frontend и Playwright. Отдельная проверка nginx запускает `nginx -t` и проверяет JSON-ошибки 413/503, допустимый размер запроса, request_id и отсутствие приватных данных в логах. Локальные результаты: [docs/validation.md](docs/validation.md).
