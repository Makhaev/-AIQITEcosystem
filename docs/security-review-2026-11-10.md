# Проверка безопасности 10.11.2026

Проверены публичные сценарии входа и восстановления, проверки прав на API и вложения, обработка пользовательских данных, зависимости npm/Go и production-настройки. Это проверка исходников и известных уязвимостей зависимостей, а не гарантия отсутствия всех возможных ошибок.

## Исправления

1. **Общий лимит восстановления за прокси.** `recovery-request` и `accept-link` использовали адрес Caddy вместо адреса посетителя. Один посетитель мог исчерпать лимит для остальных. Теперь вход и восстановление используют общий `httpx.ClientIP`: заголовок `X-Real-IP` учитывается только при `TRUST_PROXY=true`, некорректный заголовок заменяется адресом соединения. IPv4-mapped IPv6 приводится к IPv4, чтобы одна сеть не получала два разных лимита. Caddy в production перезаписывает этот заголовок.
2. **Дорогая обработка неверных ссылок.** Корректная по формату, но неизвестная/просроченная/использованная ссылка запускала bcrypt и доходила до общей блокировки административных операций. Теперь доступность ссылки проверяется раньше. Окончательная проверка одноразовости и срока действия остаётся внутри исходной транзакции, поэтому параллельное использование и отзыв ссылки по-прежнему защищены.
3. **Устаревшие Go и библиотеки.** Закреплены Go 1.26.11, pgx 5.9.2, x/text 0.43.0 и исправленный upstream-коммит x/crypto `v0.58.1-0.20261009181718-2f1f834330b2`. Коммит x/crypto выбран по исправленной версии из базы Go; на дату проверки стабильный тег 0.58.0 ещё содержал зарегистрированную проблему SSH. Приложение использует bcrypt, а не SSH, но обновлено всё дерево модулей.
4. **Автоматическая проверка.** В CI добавлены govulncheck 1.9.0 и npm audit с порогом high. Docker и CI используют одну версию Go.

Исправления применяются с текущей схемой БД без новых миграций. Лимиты остаются 30 запросов за 15 минут на адрес, отдельно для входа, запроса восстановления и применения ссылки.

## Подтверждённые записи зависимостей

- [Исправления безопасности Go 1.26.11](https://go.dev/doc/devel/release#go1.26.11).
- pgx: [GO-2026-4771](https://pkg.go.dev/vuln/GO-2026-4771), [GO-2026-4772](https://pkg.go.dev/vuln/GO-2026-4772), [GO-2026-5004](https://pkg.go.dev/vuln/GO-2026-5004). SQL-инъекция из последней записи требует нестандартного simple protocol и специфического SQL; наличие этой версии библиотеки само по себе не доказывает эксплуатацию в текущих запросах проекта.
- Исходные x/text и x/crypto также попадали в диапазоны уязвимых версий в базе Go/OSV. После обновления проверка на уровне модулей даёт `No vulnerabilities found.`

## Проверки

- `npm audit --json`: 0 известных уязвимостей.
- `npm run build`: успешная сборка frontend.
- `govulncheck -scan=module`: известных уязвимостей в итоговых модулях нет.
- `GOOS=linux govulncheck ./...`: известных уязвимостей в вызываемом коде нет.
- Регрессионные тесты: изоляция IP за доверенным прокси, игнорирование поддельного заголовка без доверия, исчерпание лимитов, обработка неизвестной ссылки при занятой административной блокировке, одноразовость/отзыв/срок действия ссылок.
- Браузерные тесты входа и валидации пароля: 4 проверки desktop/mobile-360 прошли. Эталонные скриншоты восстановлены после прогона.
- `go vet ./...`: успешно.
- Linux-сборка `server` и `admin` с Go 1.26.11 и `CGO_ENABLED=0`: успешно. Локальная проверка использовала `-buildvcs=false`, поскольку sandbox Git не доверяет владельцу рабочей копии; код бинарников от этого не меняется.
- `go test -json -count=1 -timeout=20m ./...` с PostgreSQL: успешно, включая все 54 интеграционных сценария и дополнительные подслучаи. Для тестов использована отдельная БД `aiq_security_test`; подробный журнал сохранён в `.cache/security-go-test.jsonl`.

Команда полного прогона с PostgreSQL: `go test -count=1 -timeout=20m ./...` при заданной `TEST_DATABASE_URL` отдельной тестовой БД. Первичный прогон во время подготовки завершился с ошибкой; приведённый успешный результат относится к полному повторному прогону на итоговых исправленных зависимостях.

## Границы проверки

Секреты в отслеживаемых исходниках по проверенным шаблонам не обнаружены. Установка Go launcher без доступа к сети требует заранее установленного toolchain 1.26.11. Конфигурация `TRUST_PROXY=true` предполагает, что backend доступен только через контролируемый proxy, как в production Compose. Сетевая недоступность IP из части российских сетей относится к маршрутизации и требует отдельного решения у хостинга.

Первичная проверка и тесты выполнены в локальной рабочей копии. Публикация в GitHub и обновление production выполняются отдельным шагом после проверок, с резервной копией БД и сохранением текущего образа backend для отката. Проверка действующих контейнеров подтвердила статус healthy у backend, frontend и PostgreSQL. Исправленный образ `golang:1.26.11-alpine` доступен в реестре для развёртывания.
