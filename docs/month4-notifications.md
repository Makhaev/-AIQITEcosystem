# M4-10 — уведомления

Реализовано 29 октября 2026 года. В рабочей сессии согласовано использование существующего SMTP (`SMTP_*`). Для подтверждения и отмены участия подготовлен обработчик; его подключение согласовано отложить до реализации модуля регистрации на мероприятия. Карточки событий реализованы отдельно в [M4-12](month4-free-events.md).

## Каналы и получатели

Раздел **«Уведомления»** (`#/notifications`) доступен вошедшим пользователям после обязательной смены временного пароля. В нём есть страницы по 20 записей, счётчик непрочитанных, фильтр, отметка прочтения и переход в кабинет. Даты отображаются по Москве. Обновление выполняется вручную, каждые 30 секунд на открытом экране и при возвращении фокуса окна. Ошибка обновления очищает прежний список. Отметка прочтения не отключает email.

| Событие | Получатели и поведение |
| --- | --- |
| Приглашение | Email получателя с одноразовой ссылкой по существующему M4-01. Если аккаунт уже существует — уведомление в его кабинете при выпуске приглашения; для нового аккаунта — после принятия. Повторное добавление не создаёт дубль |
| Восстановление пароля | Существующий безопасный процесс M4-02 с одноразовой ссылкой; уведомление аккаунту о запросе при выпуске ссылки. Внутри приложения токен не хранится и не показывается |
| Перенос занятия | Связанные активные ученики и подтверждённые родители из прежнего и нового состава, текущий педагог с активным профилем и ролью. Учитываются отдельный перенос и допустимое изменение времени через PATCH |
| Отмена занятия | Семья участников и текущий педагог. Повтор сохранения уже отменённого состояния не создаёт новое уведомление |
| Назначение задания | Аккаунт ученика и подтверждённые родители при создании назначения |
| Результат проверки работы | Ученик и подтверждённые родители при принятии попытки или возврате на доработку. Сообщается только факт проверки; содержание решения открывается в кабинете в пределах прав |
| Публикация отчёта | Ученик и подтверждённые родители. Одна доставка на публикацию, получателя и канал; заменённая или отозванная версия больше не показывается и не отправляется из очереди |
| Ответ на обращение | Только автор обращения. Второй родитель того же ребёнка не получает уведомление об этой переписке. Поддерживаются обращения без ребёнка |
| Подтверждение / отмена участия | Подготовлен `notify.Participation(ctx, tx, eventID, revision, studentID, confirmed)`. Будущий модуль вызывает его в транзакции разрешённого перехода участия. Сейчас пользовательского сценария регистрации на мероприятия нет и эти уведомления автоматически не возникают |

Служебная роль не расширяет семейную рассылку. Администратор не видит чужой список уведомлений. Для уведомления педагога заново проверяются назначение на занятие, профиль и роль. Общие уведомления об аккаунте не требуют семейной связи.

## Безопасный текст

Тема письма берётся из фиксированного списка, например «Работа проверена — AIQ Core». Текст обычного уведомления:

```text
В вашем кабинете новое уведомление. Подробности доступны после входа:
https://адрес-сайта/#/notifications
```

Имена детей, темы обращений, тексты ответов, оценки, причины решений, названия заданий, отчёты, вложения, внутренние наблюдения и их трактовки в обычное письмо не включаются. Модуль событий не принимает произвольный текст для рассылки. Для приглашения и восстановления остаются отдельные минимальные письма с одноразовой ссылкой и сроком действия; иначе получатель не смог бы подключиться или восстановить вход.

Ссылки не предоставляют права. При чтении списка, подсчёте, отметке прочтения и непосредственно перед передачей email проверяются актуальные роли, блокировка, семейная связь и состояние источника. После отзыва доступа уведомление исключается из списка, ожидающее письмо переводится обработчиком в `failed / recipient_unavailable`. Уже переданное SMTP письмо и отправка, начавшаяся до отзыва, не могут быть отозваны приложением.

## Надёжность доставки

Миграция `028_notifications.sql` добавила общий список и первоначальную очередь. [M4-11](month4-outbox.md), миграция `029_notification_outbox.sql`, переносит доставку в `notification_deliveries`. Уведомление и доставка записываются в той же транзакции, что и событие. Ошибка записи откатывает событие; откат события не оставляет уведомлений. Уникальность доставки определяется событием, его версией, получателем и каналом; несколько детей или ролей одного получателя не создают несколько писем.

Обычные email отправляет фоновый обработчик в процессе backend. Он проверяет очередь каждые 5 секунд, обрабатывает до 20 записей за проход и использует `FOR UPDATE SKIP LOCKED` для работы нескольких экземпляров. Вызов SMTP ограничен по времени. В одном цикле не более пяти попыток; интервалы четырёх повторов — 30, 60, 120 и 240 секунд. Это технические интервалы доставки, не срок ответа сотрудника на обращение.

Очередь переживает перезапуск и восстанавливает прерванные обработки. Состояния: `pending`, `processing`, `sent`, `failed`. `sent` означает только передачу SMTP; `delivered_at` заполняется лишь по проверенному подтверждению провайдера и для текущего SMTP остаётся пустым. Приглашения и восстановление сохраняют специальные процессы M4-01/M4-02, без повторения одноразовых токенов через общую очередь. Без SMTP обычные уведомления доступны внутри приложения; после исчерпания попыток администратор может повторить неудачные отправки через «Доставка уведомлений».

SMTP не обеспечивает строго однократную доставку: при сбое после принятия письма провайдером и до фиксации результата в БД повтор возможен. Уведомление внутри приложения остаётся единственным. Логи обработчика содержат только общий код ситуации и ID уведомления, без адреса, токенов и ошибок провайдера.

## Эксплуатация

Нужны доступный пользователям `APP_ORIGIN`, `SMTP_HOST`, `SMTP_FROM`, согласованные `SMTP_PORT`, `SMTP_TLS_MODE` и при необходимости пара `SMTP_USERNAME`/`SMTP_PASSWORD`. Используется проверяемый TLS/STARTTLS из [M4-01](month4-invitations.md). Нового провайдера, аккаунта или зависимости модуль не создаёт. Backend запускает обработчик автоматически после миграций; отдельная служба не нужна.

Проверка очереди оператором в рабочей БД без персональных данных:

```sql
SELECT channel, status, count(*) AS total, min(created_at) AS oldest
FROM notification_deliveries GROUP BY channel, status;
SELECT count(*) AS retrying, min(next_attempt_at) AS next_retry
FROM notification_deliveries WHERE channel='email' AND status='pending' AND attempts>0;
```

После исправления SMTP ожидающие записи продолжат автоматические попытки с повторной проверкой доступа; окончательные ошибки требуют ручного повтора. Прочтение и отправка — разные состояния. Ротация записей и пользовательское отключение отдельных типов email в эту задачу не включены. Реальная доставка через эксплуатационного провайдера требует проверки на настроенном стенде; при разработке письма реальным пользователям не отправлялись.

## API и проверки

Контракт: [openapi-notifications.yaml](openapi-notifications.yaml). `GET /api/v1/notifications?page=1&unread=true` возвращает собственный список; `POST /api/v1/notifications/{id}/read` требует CSRF и идемпотентно отмечает доступную запись прочитанной. Все ответы `private, no-store`. Публичного API для произвольной отправки событий или писем нет.

`notifications_integration_test.go` проверяет реальные бизнес-операции с PostgreSQL, приватность двух родителей, CSRF, недоступные ID, атомарный откат, повторы SMTP, конкурирующих обработчиков, отзыв доступа, события занятий, заданий, проверки работ, публикаций, аккаунта и обработчик будущих мероприятий. `notifications.spec.ts` проверяет фильтр, прочтение, очистку при ошибке, запоздавшие ответы, доступность и ширину 360 px.

29 октября 2026 года выполнены:

- `go test -p 1 ./... -count=1` с отдельной PostgreSQL и `TEST_DATABASE_URL` — успешно; пакет интеграционных проверок `internal/app` завершился за 276,7 секунды. Проверки, требующие отдельного эксплуатационного окружения резервного копирования, этот запуск не заменяет.
- `go vet ./...`, сборка backend и `npm run build` — успешно. Vite сохраняет предупреждение о размере основного JS-файла около 503 кБ.

- 18 Playwright-сценариев в `notifications`, `family-requests`, `family-access`, `parent-portal` на desktop и 360 px — успешно; API в этих UI-тестах подменяется. Мобильный экран дополнительно просмотрен визуально.

Проверки выполнялись с тестовыми аккаунтами и подменённым отправителем писем; существующие тесты SMTP отдельно проверяют транспорт через TLS/STARTTLS. Рабочая БД и эксплуатационная рассылка не запускались.
