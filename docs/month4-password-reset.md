# M4-02 — восстановление пароля

Реализовано 26 октября 2026 года. Применяется к аккаунтам сотрудников, родителей и учеников.

## Пользовательский сценарий

1. На странице входа нажать «Забыли пароль?» (`#/forgot-password`) и указать email.
2. Независимо от существования или блокировки аккаунта сайт отвечает: «Если аккаунт доступен, мы отправим письмо со ссылкой для восстановления пароля. Ссылка действует 30 минут».
3. Открыть ссылку из письма, задать и повторить новый пароль. Используются общие правила: минимум 12 символов, максимум 72 байта UTF-8. Новый пароль должен отличаться от текущего.
4. После успеха все сессии пользователя завершены. Войти заново с новым паролем.

После восстановления администратор входит по новому паролю без дополнительного второго фактора.

## Безопасность и API

- `POST /api/v1/auth/password-reset/request`, JSON `{ "email": "user@example.org" }`: `202` с одинаковым сообщением; `429` при превышении лимита IP.
- `POST /api/v1/auth/password-reset/confirm`, JSON `{ "token": "…", "password": "…" }`: `204`; `400 reset_invalid` для неправильной, просроченной, отозванной или использованной ссылки; `400 validation_error` для пароля; `429` при превышении лимита попыток.
- Оба запроса доступны без авторизации, но требуют обычные Origin, cookie CSRF и `X-CSRF-Token`. CSRF получают через `GET /api/v1/auth/csrf`.
- Токен — 32 случайных байта из криптографического генератора, кодирование base64url. В PostgreSQL сохраняется только SHA-256; срок — 30 минут с выпуска. Повторный выпуск заменяет предыдущую ссылку.
- Ссылка передаёт токен во фрагменте `/#/reset-password?token=…`, который не отправляется HTTP-серверу или в Referer. Форма убирает его из текущей записи истории, хранит только в памяти и передаёт в JSON. После обновления страницы нужно снова открыть исходное письмо.
- Под блокировкой строки пользователя повторно проверяются состояние аккаунта, хеш и срок. Погашение ссылки, обновление пароля, очистка счётчика неудачных входов, снятие требования смены временного пароля, отзыв всех сессий и Audit Log `auth.password_reset` выполняются одной транзакцией.
- Обычная смена пароля, административный сброс, блокировка и разблокировка отзывают старые ссылки через триггер миграции 022. Само восстановление не разблокирует аккаунт.
- HTTP-логи не содержат тело, query, cookies или секреты. SMTP-ошибки журналируются только обезличенным типом. Audit Log содержит ID и имя изменённого поля, без пароля или токена.

## Лимиты

Счётчики находятся в PostgreSQL и общие для экземпляров приложения; ключи хешируются с разделением назначения. Окно фиксированное, 30 минут; отказ не продлевает окно.

| Действие | Ограничение | Ответ при превышении |
| --- | --- | --- |
| Запрос по IP | 20 запросов | `429` |
| Запрос по нормализованному email | 5 запросов, включая неизвестные адреса | Тот же `202`, без отправки |
| Установка пароля по IP | 30 попыток, включая неверный формат токена | `429` |
| Установка пароля по корректно оформленному токену | 5 попыток, включая неподходящие пароли | `429` |

IP определяется так же, как при входе. `X-Real-IP` учитывается только при включённом `TRUST_PROXY`; прокси должен перезаписывать его. Неуспешные попытки восстановления не блокируют вход по текущему паролю. Периодическая очистка удаляет просроченные токены и устаревшие лимиты.

## Эксплуатация

Нужны миграция `022_password_reset.sql`, существующие настройки `SMTP_*` и доступный пользователям `APP_ORIGIN` (см. [SMTP M4-01](month4-invitations.md)). Письма отправляются через TLS/STARTTLS с проверкой сертификата.

Поиск аккаунта и SMTP выполняются после приёма запроса в фоне, чтобы длительность почтовой доставки не раскрывала существование аккаунта. Одновременно выполняются максимум 32 задания на процесс; при заполнении — `503` для любого email. Срок одного задания ограничен 12 секундами. При ошибке доставки выданная ссылка отзывается. Ответ `202` означает приём запроса, а не гарантию доставки. Если SMTP не настроен, внешний ответ остаётся одинаковым, а в серверном логе появляется обезличенная ошибка.

Очередь находится в памяти: остановка процесса может прервать отправку. Автоматических повторов и постоянной очереди нет; пользователь может повторить запрос с учётом лимитов. Сырые токены в БД или очередь на диске не записываются.

Контракт: [OpenAPI восстановления пароля](openapi-password-reset.yaml). Проверки: `backend/internal/app/password_reset_integration_test.go`, `frontend/tests/password-reset.spec.ts`.

- `go test -count=1 ./...` с `TEST_DATABASE_URL` на отдельном локальном PostgreSQL — успешно; тесты используют изолированные схемы. Новые проверки покрывают одноразовость, параллельное использование, срок (включая истечение во время проверки), отзыв сессий и ссылок, правила пароля, лимиты, блокировку аккаунта, отказ SMTP и отсутствие секретов в логах.
- `go build ./...`, `go vet ./...`, `npm run build` — успешно.
- Playwright: `tests/password-reset.spec.ts` и `tests/invitations.spec.ts` — 20 успешных сценариев в установленном Chrome на desktop и ширине 360 px, включая axe-проверки доступности новых форм.
- Реальные письма пользователям не отправлялись: серверные сценарии используют тестовый отправитель, браузерные — подменённый API. Приёмка доставки через эксплуатационный SMTP этим прогоном не подтверждается.
