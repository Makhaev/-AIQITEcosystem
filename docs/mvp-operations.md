# AIQ: инструкция подготовки и сопровождения MVP

Инструкция относится к основной рабочей копии проекта. На 05.11.2026 сервер, домен и внешнее хранилище не предоставлены; пользователь выбрал локальную подготовку. Наличие конфигураций не подтверждает удалённый запуск.

## 1. Проверенная версия и локальная работа

До выпуска записать полный SHA и ссылку на успешный CI. Использовать одну ветку и согласованный набор миграций. Не копировать миграции 013/014 из `.local/reacceptance`: там эти номера относятся к другим изменениям.

CI проверяет Go с PostgreSQL и race detector, frontend, браузерные сценарии, основной цикл с настоящим API, сценарии отказа резервирования, production Compose и сборку контейнеров. Локальные команды проверок описаны в [составе выпуска](pilot-release.md). Для Go обязательно задать `TEST_DATABASE_URL` отдельной тестовой БД, иначе интеграционные тесты пропускаются.

Для тестов резервирования нужны Python 3 и POSIX shell. Они используют подставные Docker и хранилище в отдельной временной папке, не подключаются к рабочей БД:

```sh
python3 -m unittest discover -s deploy/tests -v
```

На Windows можно задать `AIQ_TEST_SHELL=C:/Git/bin/bash.exe` и выполнить ту же команду через `python`. Эти тесты проверяют порядок действий и обработку отказов; реальный Docker и внешнее восстановление проверяются отдельно.

## 2. Подготовка будущего сервера

Нужны Linux с Docker Compose, домен с доступом к DNS, внешнее закрытое хранилище, ответственный оператор и канал уведомлений. До размещения согласовать состав пилота, допустимую потерю данных, срок восстановления и срок хранения копий.

1. Разместить выбранную версию в `/opt/aiq` либо изменить этот путь в unit-файлах ниже.
2. Подготовить `.env.production` по `deploy/.env.production.example`, ограничить права до 600. Для существующей БД сохранить действующий пароль. Не выводить заполненный Compose в публичные логи.
3. Пройти [инструкцию HTTPS-развёртывания](pilot-release.md#развёртывание-по-https). При обновлении сначала получить проверенную копию БД; при первой установке — создать администратора по инструкции.
4. Проверить readiness, сертификат, HTTP → HTTPS, защищённые cookies, вход каждой роли, загрузку допустимого файла 10 МиБ, сохранность данных после перезапуска.

Не запускать одновременно локальный и production Compose с одинаковым именем проекта на одном хосте. Не выполнять `docker compose down -v`: это удаляет том БД.

## 3. Ручная резервная копия

Из корня проекта на сервере:

```sh
sh deploy/backup.sh
```

Скрипт создаёт уникальный временный файл внутри контейнера и уникальный `.partial` на хосте, проверяет оглавление дампа, затем переименовывает завершённую копию в `.dump`. Права файла — 600. Временные файлы удаляются при обычном завершении и обрабатываемой ошибке. Незавершённая копия не заменяет предыдущую исправную. После аварийного выключения могут остаться временные файлы: проверять их вручную, не принимать `.partial` за резервную копию.

По умолчанию используется `.env.production`; `AIQ_ENV_FILE` позволяет задать абсолютный путь к другому production env-файлу. `sh deploy/backup.sh --print-path` возвращает путь к завершённому дампу для автоматизации. Дампы содержат данные пользователей, включая файлы модулей и отчётов, поэтому их нельзя публиковать.

## 4. Внешние зашифрованные копии

Подготовлен вариант с restic на Linux-хосте. Нужны установленный restic, `flock` из util-linux, Docker Compose и доступ к отдельному репозиторию вне сервера AIQ. Вложения уже находятся в PostgreSQL и входят в дамп; переносить их в другое хранилище для этого этапа не требуется.

1. Создать закрытый внешний репозиторий. Выдать оператору только необходимые права. Для политики удаления требуется право удаления объектов; при использовании неизменяемого хранилища политику согласовать отдельно.
2. Установить `deploy/backup.env.example` как `/etc/aiq/backup.env` с правами 600 и заменить примеры реальными значениями. Шаблон рассчитан на S3-совместимое хранилище; выбор провайдера не сделан. Это синтаксис `EnvironmentFile`, а не shell-скрипт; не выполнять файл через `source`.
3. Сохранить отдельный случайный пароль шифрования в `/etc/aiq/restic-password` с правами 600. Сохранить защищённую копию пароля и доступов вне сервера: без них восстановление после потери сервера невозможно.
4. Однократно выполнить `restic init` с безопасно загруженными переменными из файла окружения. Для уже существующего репозитория выполнить `restic snapshots`; не переинициализировать его.
5. Запустить `sh deploy/backup-offsite.sh` с теми же переменными. Скрипт блокирует параллельную доставку, создаёт локальный дамп, выполняет `restic backup`, проверку метаданных `restic check` и только затем удаление старых снимков с тегом `aiq-mvp`.

`AIQ_BACKUP_KEEP_DAILY=7` сохраняет ежедневные точки в пределах существующих успешных дней. Это предложенная настройка, её нужно согласовать. Проверка метаданных не заменяет восстановление содержимого. Локальные дампы автоматически не удаляются: оператор контролирует свободное место и отдельно согласует локальную ротацию.

Для первого ручного запуска и инициализации можно использовать systemd, который прочитает `EnvironmentFile` без вывода значений:

```sh
sudo systemd-run --wait --pipe --collect --property=EnvironmentFile=/etc/aiq/backup.env /usr/bin/restic init
```

Эта команда предназначена только для нового репозитория. Для существующего заменить `init` на `snapshots`. Проверить путь к restic на целевой системе.

## 5. Расписание и контроль ошибок

Проверить пути `/opt/aiq` и `/etc/aiq/backup.env` в шаблонах. Установить unit-файлы с правами 644:

```sh
sudo install -m 644 deploy/systemd/aiq-backup.service /etc/systemd/system/aiq-backup.service
sudo install -m 644 deploy/systemd/aiq-backup.timer /etc/systemd/system/aiq-backup.timer
sudo systemctl daemon-reload
sudo systemctl start aiq-backup.service
sudo systemctl status aiq-backup.service
sudo systemctl enable --now aiq-backup.timer
sudo systemctl list-timers aiq-backup.timer
```

Предложенное расписание — ежедневно в 03:00 по Москве, со случайной задержкой до 5 минут; пропущенный запуск выполняется после включения сервера. Unit выполняется системным пользователем root и имеет доступ к Docker; при выборе другого пользователя отдельно настроить права. Не делать файлы секретов общедоступными.

Ошибки скрипта дают ненулевой код и переводят сервис в failed. Проверять `journalctl -u aiq-backup.service` и время последней успешной внешней копии. Перед запуском пилота подключить уведомление ответственному через выбранную систему мониторинга и проверить его доставку при искусственном отказе. Автоматическая отправка уведомлений в этом шаблоне не настроена; один активный timer не закрывает требование оповещения.

## 6. Проверка восстановления

Проводить после настройки внешнего хранилища, затем по согласованному расписанию и после существенных изменений схемы. Использовать внешний снимок, отдельный каталог и новую БД, не рабочую.

1. Выполнить `restic snapshots --tag aiq-mvp` и записать идентификатор нужного снимка. Загрузить его командой `restic restore ИДЕНТИФИКАТОР --target /закрытый/новый/каталог` с теми же переменными окружения.
2. Найти восстановленный `.dump`, проверить его оглавление через `pg_restore --list`. Путь внутри restic соответствует абсолютному пути исходного дампа; не предполагать, что файл лежит прямо в корне каталога восстановления.
3. Создать новую БД с уникальным именем в изолированном PostgreSQL. Выполнить `pg_restore --no-owner --exit-on-error -d НОВАЯ_БД ПУТЬ_К_ДАМПУ` с безопасно переданными параметрами подключения. Не использовать `--clean` для рабочей БД.
4. Сравнить миграции, основные количества записей, семейные связи, посещаемость, отчёты, имена и контрольные суммы байтов вложений с ожидаемыми значениями выбранного снимка. При действующей системе текущие количества уже могут отличаться — сравнение вести с зафиксированной точкой копирования.
5. Запустить тот же SHA приложения с восстановленной БД на отдельном порту/домене, проверить вход, доступ семьи и скачивание файлов. Доступ к восстановленному окружению ограничить как к данным рабочей системы.
6. Записать дату снимка, возраст данных, длительность восстановления и результат. Только измеренное восстановление подтверждает согласованные RPO/RTO.

Не удалять исходную рабочую БД и внешнюю копию после проверки. Удаление временного окружения выполнять отдельно по проверенным именам после сохранения результата.

## 7. Обновление и сбой

Перед обновлением записать текущий SHA, проверить наличие внешней копии и возможность её восстановления. Выпускать только версию с успешным CI, применять миграции через штатный старт backend. После обновления проверить readiness, вход, журнал, отчёты и файлы.

При недоступности проверить сервисы Compose, readiness и журналы backend. HTTP-журнал содержит идентификатор запроса, метод, шаблон маршрута, статус и длительность; параметры URL, cookies и тело запроса не журналируются. В обращении пользователя достаточно времени, действия и идентификатора запроса — пароль не нужен.

Возврат прежнего образа допустим только при подтверждённой совместимости с текущей схемой. Если совместимость неизвестна, остановить обновление и подготовить исправление либо восстановление в отдельное окружение. Восстановление дампа поверх рабочей БД требует отдельного плана переноса и решения ответственного о допустимой потере новых данных.

## 8. Протокол допуска

Пока нет целевого сервера и внешнего хранилища, соответствующие проверки остаются открытыми. Не отмечать их выполненными по результатам тестов с подставными сервисами.
