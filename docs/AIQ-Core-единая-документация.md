При нескольких ролях разрешения суммируются в пределах доступных объектов. Роль куратора не открывает контакты всех учеников педагогу: полная карточка доступна только для закреплённого ученика. ## 4. Основные правила работы

### 4.1. Ученики, родители и группы

- Ученики и родители являются учебными карточками; собственных кабинетов и аккаунтов для них нет.
- У родителя требуется телефон или email. Совпадающие контакты вызывают предупреждение, но не объединяют людей автоматически; совпадение имени само по себе не считается дублем.
- Один родитель может быть связан с несколькими детьми. Повторная пара ученик/родитель и второй основной контакт одного ученика запрещены.
- Архивирование сохраняет историю. Перевод ученика выполняется в транзакции и сохраняет предыдущее зачисление.
- Вместимость и повторное активное зачисление контролируются также в БД, включая конкурентные запросы.

### 4.2. Расписание, журнал и история

- Время вводится и показывается по Москве; API передаёт время с часовым поясом.
- Пересекающиеся интервалы для одной группы или педагога запрещены; отменённое занятие не занимает интервал.
- При первом открытии журнала состав фиксируется по зачислениям на дату занятия. Последующее изменение группы не переписывает этот состав автоматически.
- Статусы отметки: `present` — присутствовал, `late` — опоздал, `absent` — отсутствовал, `excused` — уважительная причина, `unmarked` — не отмечен. Комментарий ограничен 500 Unicode-символами.
- Сохранение нескольких отметок атомарно: ошибка одной записи отменяет всю операцию.
- Завершение допускается после окончания занятия и при отсутствии неотмеченных включённых участников. Администратор может исправлять завершённый журнал; педагог работает в пределах своих разрешённых операций.
- Перенос даты после фиксации состава выполняется через отдельную административную операцию. У оставшихся и возвращённых участников сохраняются отметки; исключённые строки остаются в истории и не участвуют в актуальном расчёте.
- Снимок завершённого занятия сохраняет исторические названия. Старые данные без достоверного снимка явно помечаются `legacy_unknown`; исторические значения не выдумываются.

### 4.3. Задачи

| Переход | Кто может выполнить |
| --- | --- |
| `todo → in_progress` | Ответственный, администратор, руководитель |
| `todo → cancelled` | Постановщик, администратор, руководитель |
| `in_progress → done` | Ответственный, администратор, руководитель |
| `in_progress → cancelled` | Постановщик, администратор, руководитель |
| `done → in_progress` | Постановщик, администратор, руководитель |
| `done → cancelled` | Постановщик, администратор, руководитель |

Прямой переход `todo → done` запрещён. Из `cancelled` задача не открывается. Повтор текущего статуса не меняет дату закрытия. При переходе из открытого статуса в закрытый устанавливается `closed_at`; при повторном открытии дата очищается. Переход между закрытыми статусами сохраняет прежнюю дату. Старые неизвестные даты остаются `null`.

### 4.4. Показатели

Посещаемость в Dashboard и Student 360 считается по одной формуле:

```text
(present + late) / (present + late + absent + excused) × 100%
```

Учитываются отметки включённых участников завершённых занятий. Запланированные и отменённые занятия, исключённые участники и `unmarked` не входят в расчёт. При отсутствии данных результат — `null`, а не `0%`. Проценты отдельных групп не усредняются.

Период Dashboard по умолчанию — полный текущий московский месяц. Только показатель посещаемости зависит от выбранного периода; остальные карточки показывают соответствующие текущие количества.

## 5. Архитектура и данные

```text
Браузер: React + TypeScript
          ↓
Vite proxy при разработке / nginx в Docker
          ↓
Go API: net/http, авторизация, роли, валидация
          ↓
PostgreSQL: учебные данные, сессии, ограничения, история, audit
```

Backend — модульный монолит на Go, доступ к PostgreSQL через pgx без ORM. Frontend — React, TypeScript и Vite. Для разработки нужны Go 1.24+, PostgreSQL 17 и Node.js 22.12+; точные зависимости закреплены в `go.mod` и `package-lock.json`. Конфигурация Compose использует `postgres:17.10-alpine`.

Основные таблицы: `users`, `user_roles`, `sessions`, `login_rate_limits`, `teachers`, `students`, `parents`, `student_parents`, `programs`, `program_modules`, `groups`, `group_enrollments`, `lessons`, `lesson_participants`, `attendance`, `tasks`, `audit_logs`, `lesson_snapshot_versions`, `lesson_reschedules`, `schema_migrations`.

**Базовый вариант R10 выполнен:** ученики, родители и посещаемость выделены в отдельные модули; объединённый `families` удалён. Обработчики используют сервисы и не зависят от PostgreSQL. Сервис задаёт операции, чистые правила и публичные ошибки; репозиторий выполняет SQL, транзакции и проверки актуальных связанных записей. Подготовка итоговой PATCH-карточки вызывается политиками сервисного слоя после блокировки прежней записи внутри транзакции.

В `lesson_participants` хранятся ID занятия/группы/зачисления/ученика, имя на момент снимка и признак включения. `attendance` хранит статус, комментарий и временные метки; её PK одновременно является FK на участника с тем же прежним ID. Запись в одну таблицу не подменяет данные другой. Представление `attendance_records` объединяет поля для чтения журнала, истории и показателей. Общие права находятся в `platform/access`, блокировки занятия — в `platform/lessonstore`, формула процента — в `platform/attendance`. Подробности: [схема БД](database-schema.md).

| 016 | Разделение сохранённого состава `lesson_participants` и отметок `attendance` с сохранением ID, имён, отметок, комментариев и временных меток |

Миграции выполняются при запуске сервера и команды администратора либо отдельно через migrate. Применение учитывается в `schema_migrations`, защищено транзакцией и advisory lock. Применённые миграции не редактируют: изменения добавляют новым номером. Обратных миграций нет; возврат версии требует плана восстановления и совместимости приложения с БД.

## 6. API и защита

Префикс API — `/api/v1`. Основные группы маршрутов: `/auth`, `/users`, `/teachers`, `/students`, `/parents`, `/programs`, `/groups`, `/lessons`, `/tasks`, `/dashboard`, `/audit-logs`.

Особые операции: `/parents/contact-matches`, `/students/{id}/overview`, `/groups/{id}/enrollments`, `/lessons/{id}/attendance`, `/lessons/{id}/roster`, `/lessons/{id}/complete`, `/lessons/{id}/cancel`, `/lessons/{id}/reschedule`, `/lessons/{id}/snapshot`, `/lessons/{id}/snapshot-history`, `/tasks/{id}/status`.

Списки возвращают `items`, `total`, `page`, `page_size`. Размер страницы по умолчанию — 20, максимальный — 100. `total` учитывает фильтры и права. Сортировка дополняется ID; при конкурентном изменении данных границы страниц могут сдвигаться.

Ошибки имеют поля `code`, `message`, `field_errors`, `request_id`. Основные статусы: 400 — неверные данные, 401 — требуется вход, 403 — нет прав/ошибка CSRF, 404 — объект не найден или недоступен, 409 — конфликт, 415 — требуется JSON, 429 — лимит попыток, 500 — внутренняя ошибка, 503 — неготовность сервиса.

Пароли хешируются bcrypt; длина — минимум 12 Unicode-символов и максимум 72 байта UTF-8. Сессия действует 12 часов. Случайный токен передаётся в host-only HttpOnly cookie с `SameSite=Strict`, в БД хранится его SHA-256-хеш. При HTTPS в `APP_ORIGIN` включается `Secure`.

Для изменяющих запросов нужны допустимый `Origin` и CSRF-токен. Перед входом клиент получает `/auth/csrf`; после входа использует новый `csrf_token`. Сессионный токен не хранится в localStorage.

Audit критического изменения записывается в той же транзакции. API не предоставляет изменение/удаление audit; БД блокирует эти операции. Новые записи содержат сведения об операции и названия изменённых полей без значений паролей, токенов, контактов и свободных текстов. Технические логи структурированы и исключают тела запросов, cookies и контактные значения.

`GET /health/live` проверяет процесс. `GET /health/ready` проверяет подключение к БД и при её недоступности возвращает 503. Эти маршруты находятся вне `/api/v1`.

### 7.3. Запуск Go и Vite без контейнеров приложения

Сначала должна быть доступна PostgreSQL с подготовленной БД и правами на миграции, включая расширение `btree_gist`. Для новой стандартной конфигурации можно запустить только БД через `docker compose up -d db`.

Второй терминал, из корня проекта:

Go не читает `.env` автоматически: при прямом запуске переменные задаются в окружении. Если локальная сборка останавливается на `error obtaining VCS status`, допустим технический обход для разработки: `go run -buildvcs=false ./cmd/server`. Он отключает запись Git-метаданных в бинарник.

### 7.4. Первый администратор

Автоматического администратора и пароля по умолчанию нет. Команда bootstrap создаёт первого администратора только в пустой системе и не сбрасывает существующие аккаунты.

Для прямого запуска, из `backend` при заданной `DATABASE_URL`:

```powershell
$env:ADMIN_EMAIL = 'admin@example.test'
$env:ADMIN_NAME = 'Администратор AIQ'
$adminSecure = Read-Host 'Пароль: минимум 12 символов' -AsSecureString
$adminPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($adminSecure)
try {
    $env:ADMIN_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($adminPointer)
    go run ./cmd/admin
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($adminPointer)
    Remove-Item Env:ADMIN_PASSWORD -ErrorAction SilentlyContinue
    Remove-Item Env:ADMIN_EMAIL -ErrorAction SilentlyContinue
    Remove-Item Env:ADMIN_NAME -ErrorAction SilentlyContinue
}
```

При Compose выполните этот блок из корня проекта, заменив `go run ./cmd/admin` на `docker compose run --rm -e ADMIN_EMAIL -e ADMIN_NAME -e ADMIN_PASSWORD admin`. Пароль не следует сохранять в файле проекта.

## 8. Порядок работы пользователя

1. Администратор создаёт сотрудников и назначает роли; сотрудники меняют временные пароли.
2. Создаются профиль педагога, ученик, родитель и семейная связь; ученику назначается куратор.
3. Создаются программа и модули, активируется программа, создаётся группа с педагогом и вместимостью.
4. Ученик зачисляется в группу с датой начала; создаётся занятие.
5. Педагог открывает журнал своего занятия. После начала сохраняет отметки; после окончания и заполнения журнала завершает занятие.
6. Куратор смотрит Student 360 закреплённого ученика. Руководитель смотрит показатели и ставит задачи доступным исполнителям.
7. Ответственный переводит задачу в работу, затем завершает её. Администратор проверяет критические действия в Audit Log.

Для демонстрации используются вымышленные данные. Автоматический учебный seed в проекте не предусмотрен.

## 9. Обслуживание и резервные копии

R12: ежедневные копии в 03:00 Europe/Moscow, семь успешных архивов, проверка
целостности и SHA-256 до публикации. При ошибке прежние копии сохраняются,
оператор видит failed/unhealthy и стадию сбоя. Перед обновлением дополнительно
выполняют `backup run`; одновременно менять схему и делать копию нельзя.

миграции. Затем отдельный экземпляр приложения проверяют через вход, Student 360,
журнал, историю, задачи и audit. Рабочая БД не перезаписывается.

[Отчёт R12](r12-backup-report.md) фиксирует фактические локальные испытания и
оставшиеся проверки инфраструктуры эксплуатации. Одна ручная команда резервирования
без восстановления не является приёмкой.

## 12. Что отсутствует, но не является автоматически обязательной доработкой этапа

В текущей версии нет кабинетов ученика и родителя, публичной регистрации, восстановления пароля по email, пользовательского экспорта данных и автоматического демонстрационного наполнения. Добавление этих возможностей требует отдельного согласования объёма. Их отсутствие не следует смешивать с обязательными оставшимися R11–R14.

Использование реальных персональных данных также требует отдельного решения по основаниям обработки, срокам хранения и процедурам удаления; функциональные тесты приложения этого не подтверждают.
