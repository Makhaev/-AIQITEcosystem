## Локальный архив

```powershell
node scripts/r14-package.mjs
```

Команда создаёт новый каталог `.cache/handover/<UTC-время>/`, архив
`aiq-platform-v0.1.0-candidate.tar`, файл `.sha256` и копию исходников с
`MANIFEST.json`. Включает текущие, в том числе незакоммиченные, файлы только из
каталогов комплекта. Исключает `.git`, `.cache`, `.env`, зависимости, сборки,
логи, ключи, дампы и тестовые конфигурации с паролями. Отказывается от symlink
и известных форматов приватных ключей/токенов; это не заменяет ручную проверку
секретов перед публикацией. Хеши скопированных файлов проверяются до архивации.

Получатель сверяет SHA-256 архива, распаковывает его в новый каталог и сверяет
файлы с `MANIFEST.json`: `node scripts/r14-verify-package.mjs <каталог кандидата>`.
Архив содержит исходники для сборки, а не готовое
развёртывание; интернет-доступ к registries и указанные toolchain нужны отдельно.
Git-история и доступ к репозиторию передаются отдельно после согласования
GitHub. Имя локального архива не меняет имя репозитория.

[Read-only аудит](reports/r14-github-audit.json) выполнен 19.10.2026 через GitHub API:

- Origin: `https://github.com/Makhaev/-AIQITEcosystem.git`; remote не изменён.
- Фактическое имя `-AIQITEcosystem` не совпадает с `aiq-platform`.
- `private=false`: репозиторий публичный; требование приватности не выполнено.
- Владелец по метаданным — `Makhaev`. Это не доказательство, что заказчик вошёл
  в нужную учётную запись и имеет административные права. Доступ заказчика не
  проверен: его GitHub identity и авторизованная сессия для аудита не предоставлены.
- [CI базового SHA](https://github.com/Makhaev/-AIQITEcosystem/actions/runs/38371068612)
  завершился `failure`: backend `go test -race ./...`; frontend успешен.
  Это прежний commit, а не текущий незакоммиченный кандидат. Новый удалённый
  прогон отсутствует, новые CI jobs не считаются выполненными.

Повторный аудит: `node scripts/r14-github-audit.mjs`. Для проверки именно
доступа владельца он выполняется в его согласованном окружении с `GH_TOKEN`
из менеджера секретов и `R14_EXPECTED_OWNER=<логин заказчика>`. Скрипт делает
только GET, не сохраняет токен; проверяет совпадение авторизованного login и
права admin. При неподтверждённых условиях возвращает код 2. В организации
могут дополнительно потребоваться SSO и подтверждение командного доступа.

Нужны отдельные решения владельца: приватность, сохранение/изменение имени
или другой целевой репозиторий, право опубликовать код, право развернуть стенд.
Они фиксируются с датой, автором и ссылкой. Поручение подготовить R14 не
содержит этих разрешений. Push в существующий публичный origin не выполнен.

## Работа через PR

1. Проверить локальные изменения и состав снимка, завести реальные задачи R01–R14
   для текущих доработок. Не присваивать вымышленные номера issue/PR.
2. После согласования места и прав публикации зафиксировать согласованный состав
   изменений в ветке, получить точный commit SHA и открыть PR с `Refs #...` /
   `Closes #...`. [Шаблон PR](../.github/pull_request_template.md) и
   [шаблон задачи](../.github/ISSUE_TEMPLATE/requirement.md) входят в комплект.
3. Дождаться успешных jobs `backend`, `frontend`, `openapi`, `proxy`,
   `docker-https`, `backup-r12`, `browser-real` на этом SHA. Backend использует
   PostgreSQL и `go test -race ./...`, vet и сборки; frontend — сборку и UI.
   Нагрузку повторить отдельно на согласованном стенде и приложить отчёт.
4. Провести ревью, обработать воспроизводимые дефекты доступа/основных операций,
   согласовать допустимые замечания и принять PR по правилам владельца.
5. Проверить итоговый merge SHA; результаты предыдущего head после изменения
   кода не переносятся автоматически. Выпуск связан с проверенным SHA.

Создание ветки сейчас не означает, что прошлые доработки проходили PR.
Прошлую историю недельных демонстраций задним числом не создаём.

## Условия оформления v0.1.0

Закрыть все пункты [чек-листа](acceptance-r14.md), получить успешный CI и
согласования, подтвердить доступы заказчика. Только после отдельного разрешения
на публикацию оформить tag `v0.1.0` на принятом SHA и GitHub Release с
[release notes](release-v0.1.0.md), архивом, SHA-256 и отчётами этого SHA.
До этого документ остаётся черновиком; tag/release не созданы.

Передать заказчику репозиторий, адрес стенда, роль/порядок получения доступа,
инструкции, отчёты и подписанный чек-лист. Пароли, токены и ключи не входят
в архив, PR или акт: передаются согласованным закрытым способом.

Допуск реальных персональных данных оформляется отдельно от функциональной
приёмки прототипа: основания обработки, состав данных, ответственные, сроки
хранения, процедура удаления и охват резервных копий ещё требуют решения.
