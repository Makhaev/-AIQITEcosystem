# AIQ: первый пилотный выпуск

Статус: локальная реализация MVP. Публичный HTTPS-адрес ещё не выпущен: нужны домен и сервер с доступом для развёртывания. Конфигурация развёртывания подготовлена, её запуск и получение сертификата на целевом сервере должны быть подтверждены отдельно.

## Состав выпуска

Обязательный сценарий: администратор создаёт карточки семьи, семейную связь, программу, группу и зачисление; приглашает педагога, ученика и родителя; педагог открывает журнал, отмечает посещаемость и завершает занятие; выдаёт задание; ученик отправляет текстовый ответ; педагог принимает работу или возвращает её на доработку; педагог сохраняет и публикует отчёт; родитель видит результат только связанного ребёнка.

Первое MVP использует текстовые задания, ответы и отчёты. Срок задания необязателен. Приглашения и восстановление передаются вручную по согласованному с заказчиком порядку. SMTP не требуется.

| Возможность | Реализация и проверка |
| --- | --- |
| Вход, выход, смена пароля, блокировка | Существующий auth + интеграционные тесты |
| Восстановление | Запрос из формы входа → проверка личности администратором → одноразовая ссылка → новый пароль; старые сессии завершаются |
| Роли и изоляция | Сотрудники: admin/leader/teacher/curator/methodist; семья: student/parent. Проверяются сервером и связями в БД |
| Семьи и педагоги | Существующие CRUD и семейные связи; новая связь карточки с аккаунтом через приглашение |
| Программы, группы, состав | Существующие CRUD, история зачислений, ограничения вместимости и связей |
| Кабинет методиста | Создание и редактирование программ и модулей, дерево содержания; реализация программ, прогресс учеников и отчёты внутри раздела; [описание и API](methodist-workspace.md) |
| Игровой прогресс ученика | Сердце и шкала HP в кабинете и заданиях: принятые работы / все задания × 100%. Ответ на проверке не засчитывается как принятая работа; задания отменённых занятий исключены. При отсутствии заданий показывается начало обучения, без ложных 100%. |
| Расписание и посещаемость | Существующие журнал, фиксация состава, отметки и завершение занятия |
| Приглашения и кабинеты | Новые экраны «Приглашения и доступ», «Семейный кабинет» |

| Публичный HTTPS | Подготовлен `deploy/compose.production.yaml`; удалённое развёртывание ещё не проверено |

Проекты, достижения, навыки, события, обращения родителей, дополнительные показатели, уведомления, материалы и настройки закрыты серверными флагами и отсутствуют в навигации. Старые разделы «Обзор», «Задачи» и общий аудит также скрыты: у них отсутствовала подтверждённая серверная реализация. Учебные «Задания» — отдельный работающий модуль. Записи аудита продолжают сохраняться. CRM, финансы, оплата и ИИ не добавлялись.

## Проверки

`backend/internal/app/pilot_integration_test.go` проверяет весь основной путь через HTTP и настоящую PostgreSQL, разные cookie-сессии и две независимые семьи. Проверяются запрет чужой работы/отчёта, недоступность черновиков, отзыв доступа после удаления семейной связи, повторная отправка работы, возврат на доработку, завершение занятия, неизменность опубликованного отчёта, ограничения приглашений и флаги. Отдельно проверяются истечение, перевыпуск, конкурентное погашение ссылки и отзыв сессий после восстановления.

`frontend/tests/pilot.live.spec.ts` проходит интерфейс с настоящим API и отдельной тестовой БД. Создание исходных учебных записей выполняется через API; приглашение, установка пароля, вход, журнал, выдача, ответ, проверка, публикация, просмотр семьёй и восстановление — через браузер. Проверяются размеры 1440×1000 и 360×800, отсутствие ошибок JavaScript и базовые требования доступности.

Остальные Playwright-тесты используют моки API и подтверждают поведение интерфейса; они не заменяют интеграционную проверку.

```powershell
# Из backend, TEST_DATABASE_URL — отдельная тестовая БД PostgreSQL 17.
go test -count=1 ./...
go vet ./...
go build ./cmd/server ./cmd/admin

# Из frontend.
npm ci
npm run build
npm run test:ui

# Живой браузерный тест: отдельная тестовая БД, backend и Vite уже запущены.
# APP_ORIGIN должен совпадать с PILOT_BASE_URL.
# AIQ_API_TARGET направляет Vite на тестовый backend.
# PILOT_ADMIN_EMAIL/PILOT_ADMIN_PASSWORD передаются через окружение.
node node_modules/@playwright/test/cli.js test --config playwright.live.config.ts
```

Результаты выполненных проверок и границы проверки фиксируются в `docs/pilot-validation.md`.

## Локальная приёмка человеком

Кабинет куратора, прогресс, отчёты и обратная связь семьи: [назначение и рабочий сценарий](curator-workspace.md).

Кабинет педагога, его группы и ученики: [настройка назначений и проверка доступа](teacher-workspace.md).

1. Войти администратором. Создать ученика и родителя; в карточке ученика нажать «Связать с родителем».
2. Создать активную программу, группу, зачисление и карточку педагога. Запланировать занятие с этим педагогом.
3. В «Приглашения и доступ» выбрать роль, карточку и email. Передать ссылку лично. Для каждой роли использовать свой браузер или приватное окно.
4. По ссылке задать пароль и войти. Педагогу открыть занятие, проверить состав журнала, сохранить посещаемость. Завершение доступно после окончания занятия и выставления всех отметок.
5. Педагогу в «Задания» выбрать занятие/ученика и выдать текстовое задание. Ученику отправить ответ; педагогу принять его с комментарием или вернуть на доработку.
6. Педагогу в «Отчёты» сохранить черновик. Родитель в этот момент не должен видеть его. Нажать «Опубликовать родителю»; обновить семейный кабинет родителя и проверить результат.
7. Проверить другой семейный аккаунт: чужой ребёнок и его результаты отсутствуют.
8. Выйти, выбрать восстановление, отправить запрос. Администратору проверить личность пользователя и выпустить ссылку; задать новый пароль и войти заново.

Приглашение действует 48 часов, ссылка восстановления — 30 минут. В БД хранится SHA-256 хеш токена. Ссылка показывается только при выпуске; новая ссылка отменяет предыдущие. Изменение пароля, прав или блокировка также отзывают выпущенные ссылки. Администратор может перевыпустить ссылку для уже приглашённого пользователя через восстановление.

## Развёртывание по HTTPS

1. Подготовить сервер с Docker Compose, направить A/AAAA домена на сервер и открыть входящие 80/443. Используется публичное доменное имя без схемы и пути.
2. Доставить исходники на сервер. В корне скопировать `deploy/.env.production.example` в `.env.production`, указать домен и случайный пароль БД из букв/цифр. Файл исключён из Git. При существующей БД сохранить её действующий пароль.
3. До обновления сохранить резервную копию. Исходный Compose и production-конфигурация используют имя `aiq-core` и том `postgres_data`, чтобы сохранить существующие контейнерные данные. Не запускать оба набора одновременно и не выполнять `down -v`.
4. Выполнить из корня:

```sh
docker compose --env-file .env.production -f deploy/compose.production.yaml config --quiet
docker compose --env-file .env.production -f deploy/compose.production.yaml up --build -d
docker compose --env-file .env.production -f deploy/compose.production.yaml ps
```

Caddy получает сертификат и перенаправляет HTTP на HTTPS при корректном DNS и доступных портах; условия описаны в [официальной документации](https://caddyserver.com/docs/automatic-https). Данные сертификатов сохраняются в отдельном томе. PostgreSQL и backend не публикуют порты на хосте. Прямые API-запросы проходят через Caddy, который заменяет `X-Real-IP` адресом клиента.

5. Для новой пустой БД создать администратора командой из README, заменив Compose-вызов на:

```sh
docker compose --env-file .env.production -f deploy/compose.production.yaml run --rm -e ADMIN_EMAIL -e ADMIN_NAME -e ADMIN_PASSWORD admin
```

`ADMIN_PASSWORD` вводится через защищённый ввод/окружение и очищается после команды. Не использовать локальные демонстрационные пароли на публичном сервере. Существующие аккаунты и данные можно перенести восстановлением проверенной резервной копии до первого старта backend.

6. Проверить `https://ДОМЕН/health/ready`, перенаправление HTTP, валидный сертификат, вход, `Secure/HttpOnly/SameSite` cookies, повторить основной сценарий с реальными пилотными аккаунтами. До этих проверок выпуск не считается размещённым.

## Резервные копии и обновление

Запускать `sh deploy/backup.sh` из Linux, перед каждой миграцией и ежедневно по расписанию. Скрипт создаёт custom-format дамп в `.cache/backups`, проверяет оглавление и выставляет права 600. Копировать дампы во внешнее закрытое хранилище; одно хранение на сервере не защищает от его потери. Конкретное внешнее хранилище и расписание нужно назначить при размещении.

Проверка восстановления выполняется в отдельной новой БД, не поверх рабочей:

```sh
docker compose --env-file .env.production -f deploy/compose.production.yaml cp .cache/backups/ИМЯ.dump db:/tmp/restore-check.dump
docker compose --env-file .env.production -f deploy/compose.production.yaml exec db createdb -U aiq aiq_restore_check
docker compose --env-file .env.production -f deploy/compose.production.yaml exec db pg_restore -U aiq -d aiq_restore_check --no-owner --exit-on-error /tmp/restore-check.dump
```

Проверить количество карточек, семейные связи, журнал и доступность API с восстановленной БД. Миграция `009_pilot.sql` только добавляет столбцы, роли, таблицы и индексы; существующие карточки и история не удаляются. Возврат старого бинарника не удаляет новые таблицы. Автоматические обратные миграции с удалением данных не предусмотрены.

## Границы первого пилота

- Ручная передача ссылок требует проверки личности получателя администратором. Нет SMTP, SMS и автоматической доставки.
- Нет вложений, загрузки файлов, оценок по шкалам, ИИ и интеграций с CRM/оплатой.
- Новые учебные представления возвращают до 500 записей; перед расширением пилота нужна пагинация и нагрузочная проверка на его реальном объёме.
- Наличие конфигурации Docker/HTTPS не подтверждает удалённое развёртывание, внешнее резервное копирование и работу DNS. Это отдельные шаги приёмки.

Куратор назначается группе в поле «Куратор группы». Список учеников и семей формируется автоматически по текущим зачислениям; индивидуальное назначение ученику отключено. Подробности и правила переноса прежних назначений: [кабинет куратора](curator-workspace.md).

Навигация кабинета куратора: обзор, мои ученики, мои группы, расписание, отчёты родителям; профиль и настройки аккаунта находятся внизу, ответы родителей открываются из верхней панели. Обзор содержит фактические причины внимания, карточка ученика — расписание, сохранённую посещаемость, задания, результаты и наблюдения. Обращения, личные задачи и отдельный учёт целей скрыты до реализации; цели и рекомендации в отчёте доступны.
