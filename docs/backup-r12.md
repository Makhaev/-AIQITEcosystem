# R12: резервирование и проверка восстановления

`backend/cmd/backup` — отдельный процесс эксплуатации. Он запускает `pg_dump -Fc`
ежедневно в **03:00 Europe/Moscow**, сохраняет **семь последних успешных копий**,
выводит JSON-статус и проверяет восстановление в новую БД. Время задаётся
`BACKUP_TIME=HH:MM`, часовой пояс фиксирован и встроен в бинарник. После простоя
выполняется одна пропущенная копия; ошибка повторяется через 15 минут.
Один запуск ограничен двумя часами. Запуск вручную не заменяет ежедневный.

## Хранилище и права

Хранилище готовит ответственный за инфраструктуру: отдельный от PostgreSQL
диск/сетевое хранилище с шифрованием данных, ограниченным доступом и резервом
места минимум под восемь полных копий и служебные файлы. Приложение само не
шифрует архив. Локальная папка на том же диске годится для испытаний, но не
подтверждает защищённое эксплуатационное хранилище. Файловая система должна
поддерживать атомарный rename внутри каталога и надёжный fsync; объектное
хранилище/S3/FUSE без этих гарантий напрямую не поддерживается.

Подключённый каталог должен **заранее существовать** и содержать файл
`.aiq-backup-store` с точными байтами `aiq-backup-v1\n` (UTF-8 без BOM).
Программа не создаёт корень хранилища: отсутствие монтирования/маркера вызывает
сбой, а не запись на диск приложения. Один корень предназначен для одной БД.

Linux: владелец — выделенная учётная запись резервирования, каталог `0700`,
архивы и манифесты `0600`; чтение другим пользователям запрещено и проверяется
при запуске. Для контейнера владелец bind-каталогов — UID/GID `70:70`.
Windows: оператор заранее отключает наследование ACL и оставляет доступ
только учётной записи службы, SYSTEM и ответственным администраторам; режим
`chmod` не заменяет ACL. Доступ к Docker daemon также даёт доступ к секретам.

`BACKUP_STATE` находится на **локальном диске отдельно от хранилища**, с такими
же ограничениями: статус ошибки остаётся доступен, даже если хранилище отключено.
Каталоги архивов не публикуются nginx и не монтируются в backend/frontend.
Архив содержит персональные данные, хеши паролей и сессии. Ни архивы, ни env-файл
с секретами не помещают в Git. Отчёты содержат только количества и хеши.

Роль резервирования: `LOGIN`, `CONNECT` к `aiq`, чтение всех таблиц и
последовательностей, включая будущие. Пример для DBA после создания роли с
паролем через защищённую сессию:

```sql
GRANT CONNECT ON DATABASE aiq TO aiq_backup;
GRANT pg_read_all_data TO aiq_backup;
```

Роль не требует SUPERUSER, CREATEDB или записи в таблицы. `pg_read_all_data`
не обходит RLS: при введении RLS права пересматриваются и прогоняется испытание.
Для восстановления используется **другая** роль с CREATEDB и правами установки
`btree_gist`; роли/секреты PostgreSQL в дамп одной БД не входят.
Для удалённого подключения используйте `sslmode=verify-full` и доверенный CA.
`sslmode=disable` допустим для изолированной внутренней сети Compose или
локального тестового кластера. Пароли URL-кодируются, секреты — в env-файле
`0600` вне Git. `DATABASE_URL` — URL `postgres://` или `postgresql://`.

## Запуск

Docker: дополните защищённый env-файл параметрами:

```dotenv
BACKUP_DATABASE_URL=postgres://aiq_backup:URL_ENCODED_PASSWORD@db:5432/aiq?sslmode=disable
BACKUP_STORE_HOST=/mnt/aiq-backups
BACKUP_STATE_HOST=/var/lib/aiq-backup
BACKUP_TIME=03:00
```

После подготовки монтирования и прав, на Linux:

```sh
printf 'aiq-backup-v1\n' > /mnt/aiq-backups/.aiq-backup-store
chmod 600 /mnt/aiq-backups/.aiq-backup-store
docker compose -f compose.yaml -f compose.backup.yaml up -d --build backup
docker compose -f compose.yaml -f compose.backup.yaml exec backup aiq-backup status
docker compose -f compose.yaml -f compose.backup.yaml logs --tail 30 backup
```

Для HTTPS-пилота используйте **три** файла во всех командах:
`-f compose.pilot.yaml -f compose.backup.yaml -f compose.backup-pilot.yaml`.
Последний подключает резервирование к закрытой сети `data`.
Сервис включается явно, чтобы пустое или незащищённое хранилище не создавалось
автоматически. Bind-mounts запрещают автоматическое создание каталогов.

Без Docker: собрать из `backend` командой `go build -o backup ./cmd/backup`,
установить PostgreSQL 17 client tools, задать переменные из
[`deploy/backup.env.example`](../deploy/backup.env.example). `PG_BIN` — необязательный
каталог `pg_dump`/`pg_restore`; по умолчанию используется PATH. Запускать
`backup serve` через службу ОС. Linux unit:
[`deploy/aiq-backup.service`](../deploy/aiq-backup.service); после настройки
учётной записи, путей и `/etc/aiq/backup.env` установить unit и выполнить
`systemctl enable --now aiq-backup`. На Windows зарегистрировать `backup.exe serve`
в используемом менеджере служб под выделенной учётной записью с автозапуском
и перезапуском после сбоя. Открытый терминал не является постоянной службой.

Внеплановая копия: `backup run`; в контейнере — `exec backup aiq-backup run`.
Параллельные запуски одной БД блокируются PostgreSQL advisory lock; блокировка
автоматически освобождается после разрыва соединения/падения процесса.

## Публикация и ротация

1. В `.partial-*` на целевом хранилище создаётся временный `database.dump`.
2. Экспортированный REPEATABLE READ snapshot используется и `pg_dump`, и
   контрольными запросами: параллельная запись приложения не рассогласует отчёт.
3. `pg_restore --file=-` полностью читает/распаковывает архив, вывод отбрасывается.
   Проверка одного `--list` была бы недостаточна.
4. Вычисляются SHA-256 и размер, файл синхронизируется, затем повторно читается
   и сравнивается. Сохраняется `manifest.json`: дата UTC, версии, размер,
   длительность, количества и SHA-256 упорядоченных JSON-строк каждой таблицы.
5. Каталог атомарно переименовывается в `aiq-<UTC timestamp>`; только такие
   каталоги доступны восстановлению. На Linux синхронизируются также каталоги.
   После публикации архив ещё раз сверяется с манифестом.
6. Только после успешной публикации удаляются самые старые копии сверх семи.
   Временные и посторонние каталоги не учитываются. При ошибке создания,
   чтения или проверки никакие предыдущие копии не удаляются. При ошибке
   ротации сохранённая новая копия остаётся, статус — failed; копий может быть
   больше семи до устранения причины и следующего успешного запуска.

Не запускайте DDL/миграции одновременно с резервированием. Контроль содержимого
сортирует строки таблиц и требует времени/временного места PostgreSQL; измерьте
это на эксплуатационном объёме. На Windows синхронизация каталога через Go
недоступна; испытание сбоя питания относится к выбранному эксплуатационному
хранилищу. После аварийного завершения `.partial-*` могут остаться: их можно
удалить после остановки резервирования, убедившись, что активного задания нет.

## Контроль и действия при сбое

`backup status` печатает `state`, `stage`, `attempt_at`, `last_success_at`,
`scheduled_day`, `backup`. Код `0` означает исправность, `1` — ошибку, отсутствие
успешной копии, копию старше 26 часов, задание дольше двух часов или недоступное
хранилище. Compose показывает `unhealthy`; daemon пишет JSON и сообщение сбоя
в stderr. Если недоступен также каталог статуса, ручная команда завершается с
ошибкой, служба пишет сбой в журнал. Секреты и stderr PostgreSQL с возможным
содержимым записей в общие журналы не выводятся.

Ответственный ежедневно проверяет статус и наличие новой копии. Внешний
мониторинг должен проверять **код `backup status`, возраст копии и состояние
службы**, а не только факт запущенного процесса. Канал уведомлений, получатели,
порог и дежурный согласуются в окружении эксплуатации; интеграция с почтой/чатом
здесь не настроена. Docker healthcheck сам уведомлений не отправляет.

При failed: сохранить статус, проверить стадию (`connect`, `storage`, `snapshot`,
`dump`, `inventory`, `archive_validation`, `publish`, `rotation`), доступность БД,
монтирование, свободное место, ACL, маркер, версии утилит и права чтения роли.
Не удалять старые копии ради повторного запуска. После исправления выполнить
`backup run`, проверить код и SHA-256/манифест новой копии, затем убедиться в
следующем ежедневном запуске. При повреждении архива выбрать другую сохранённую
копию и расследовать хранилище; не пересчитывать манифест повреждённого файла.

## Безопасное восстановление и приёмка

Остановите процесс резервирования на время выбора/восстановления, чтобы ротация
не удалила выбранную копию. Рабочее приложение останавливать для испытания не
нужно. Запускайте восстановление с доверенным архивом, под отдельной ролью,
желательно на отдельном PostgreSQL той же основной версии:

```powershell
# DATABASE_URL — подключение роли восстановления к служебной БД postgres.
# BACKUP_STORE / BACKUP_STATE / PG_BIN заданы как выше.
./backup.exe restore aiq-YYYYMMDDTHHMMSS.nnnnnnnnnZ > restore-report.json
if ($LASTEXITCODE -ne 0) { throw 'Восстановление не прошло; изучите отчёт' }
```

Идентификатор берётся из `backup status` или имени каталога. Команда проверяет
SHA-256 и размер **до создания БД**, создаёт `aiq_restore_<случайный ID>` из
`template0` и выполняет `pg_restore --single-transaction --exit-on-error
--no-owner --no-privileges`. Принимать существующее имя БД или использовать
`--clean`/`--create` команда не позволяет. Неудачная новая БД сохраняется для
диагностики. Её последующее удаление — явное действие оператора.

Отчёт содержит дату копии, версии PostgreSQL и утилит, размер, SHA-256,
длительность восстановления, целевую БД и проверки. Сравниваются количества
**и все значения строк** всех пользовательских таблиц, включая учебную историю,
посещаемость, задачи, audit и связи. Ограничения/FK создаются и проверяются самим
`pg_restore`; проверяются точный набор миграций встроенного приложения и их
безопасный повторный запуск. Для старой версии архива используйте соответствующий
бинарник, а обновление миграций проверяйте отдельным этапом.

Статус `database_verified_application_checks_required` означает, что ещё нужны
проверки приложения: направить **отдельный** backend на созданную БД, с другим
HTTP-портом/origin, проверить readiness, войти существующим аккаунтом и открыть
Student 360, историю/исправления занятий, журнал с отметками, задачи и audit.
Сверить выбранные записи с исходным контрольным набором. Bootstrap не запускать.
Результаты добавить в отчёт; восстановление CLI само по себе не закрывает R12.
После испытания возобновить резервирование и проверить его health.

Воспроизводимая автоматическая приёмка на синтетических данных:

```powershell
Set-Location backend
$env:R12_TEST_DATABASE_URL = 'postgres://TEST_USER:TEST_PASSWORD@127.0.0.1:5432/postgres?sslmode=disable'
$env:PG_BIN = 'C:/Program Files/PostgreSQL/17/bin'
$env:R12_REPORT_PATH = Join-Path (Resolve-Path ../docs/reports) 'r12-local.json'
go test ./internal/app -run '^TestR12BackupAcceptance$' -count=1 -v
```

Нужен **изолированный тестовый сервер** с правами CREATEDB/CREATEROLE. Тест сам
создаёт и удаляет только свои случайные БД и роль. Он проверяет восемь суточных
границ, фактический запуск worker при наступлении следующей минуты по реальным
часам, семь копий, ошибку pg_dump/хранилища/утилит, сохранность прежних архивов,
повторный запуск, отказ при повреждении SHA-256, фактическое восстановление,
миграции, вход через HTTP и восстановленные учебные данные. Рабочая БД не нужна.
Отчёт испытания и границы подтверждения: [R12 report](r12-backup-report.md).

Основания параметров PostgreSQL: [экспорт snapshot](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION),
[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).
