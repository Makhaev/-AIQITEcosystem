# Роли, доступ и педагоги

## Проверки на сервере

Фиксированные роли: `admin`, `leader`, `teacher`, `curator`. Неизвестные роли отклоняются при создании и изменении пользователей и ограничением таблицы `user_roles`. Разрешения нескольких ролей суммируются.

`backend/internal/platform/access` содержит явную матрицу ресурсов и действий. По умолчанию возвращается запрет. Ограниченные области `Own` и `Assigned` требуют проверки связи объекта с пользователем; разрешение на ресурс само по себе не даёт доступа ко всем ID.

| Данные / действие | Администратор | Руководитель | Педагог | Куратор |
| --- | --- | --- | --- | --- |
| Пользователи и роли | Управление | Нет | Нет | Нет |
| Профили педагогов | Чтение и управление всеми | Чтение всех | Чтение собственного профиля | Нет |
| Учебные данные | Все | Чтение всех | Свои занятия и необходимый состав | Закреплённые ученики и их обучение |
| Полная карточка ученика | Все | Все | Нет | Только закреплённые ученики |
| Посещаемость | Ввод и коррекция | Чтение | Ввод только своих занятий | Чтение своих учеников |
| Задачи | Управление | Управление | Свои задачи и их разрешённые переходы | Свои задачи и их разрешённые переходы |
| Показатели | Чтение | Чтение | Нет | Нет |
| Audit | Чтение | Нет | Нет | Нет |

Для существующих маршрутов пользователей и педагогов права проверяет middleware на каждом запросе. Репозитории повторно получают сессию и роли из PostgreSQL; изменяющие транзакции блокируют запись действующего пользователя и выполняются в общем порядке с блокировкой аккаунта и сменой ролей. Отозванная или истёкшая сессия не может завершить новую административную операцию.

Педагог получает список и количество только своего профиля через условие SQL `teachers.user_id = actor.ID`. Чужой ID возвращает 404 и не раскрывает существование записи. Куратор не имеет доступа к справочнику педагогов. GET использует повторяемое чтение, список и общее количество вычисляются в одном снимке данных.

Для будущих учебных модулей предусмотрены предикаты `StudentAllowed` и `LessonAllowed`. Их параметры — связи, загруженные сервером из БД, а не ID владельца из тела запроса. Они различают полную и минимальную карточку ученика, непосредственное назначение куратора, собственные занятия и чтение без права изменения посещаемости. Их матрица проверена unit-тестами. API учеников, занятий, задач и показателей ещё не реализованы; эти правила не заменяют необходимые проверки в репозиториях будущих модулей.

## Педагоги

Профиль хранится отдельно от `users`: ФИО, телефон, email, специализация, `active`/`archived`, необязательный `user_id`, время создания и изменения. ФИО обязательно, до 200 символов. Специализация — до 500. Email приводится к нижнему регистру; телефон — к международному формату. Контакты могут быть пустыми; совпадение имён или контактов не объединяет записи.

Связывается только существующий неблокированный пользователь с ролью `teacher`. Частичный уникальный индекс запрещает два профиля для одного пользователя, включая архивные. `user_id: null` снимает связь. Если пользователь позднее заблокирован или потерял роль, существующая связь сохраняется для истории; доступ определяется текущей сессией и ролями.

| Метод | Маршрут | Действие |
| --- | --- | --- |
| GET | `/api/v1/teachers` | Список, поиск, фильтр по статусу, пагинация с учётом прав |
| GET | `/api/v1/teachers/{id}` | Профиль с проверкой доступа по ID |
| POST | `/api/v1/teachers` | Создание администратором |
| PATCH | `/api/v1/teachers/{id}` | Изменение, архивирование и восстановление администратором |

Параметры списка: `search`, `status`, `page`, `page_size`. Поиск — буквальная подстрока ФИО без учёта регистра, включая кириллицу; `%` и `_` не становятся wildcard. Сортировка стабильна по нормализованному ФИО и ID. Размер страницы по умолчанию 20, максимум 100. При отсутствии фильтра возвращаются активные и архивные профили.

Архивирование: PATCH с `{"status":"archived"}`. ID, контакты и профиль остаются в БД. Физического удаления через API нет. `teachers.RequireActive(ctx, tx, id)` отклоняет архивного педагога с 409 `teacher_archived` и удерживает разделяемую блокировку строки до конца транзакции назначения. Будущий модуль групп/занятий обязан вызывать этот guard при новом назначении и хранить внешний ключ на `teachers`; существующие исторические назначения не пересоздаются. Проверка конкурентного назначения и архивирования выполнена на тестовом потребителе с настоящим внешним ключом PostgreSQL, а не на ещё отсутствующем API занятий.

Создание, изменение, архивирование и восстановление записываются в audit в той же транзакции. Миграция `002_teachers.sql` добавляет таблицу и индексы, а также тип объекта в audit. Прежние события остаются событиями пользователя; пароли, токены и значения контактов в audit не записываются.

Контракт: [OpenAPI](openapi.yaml). Дополнительно GET `/users?role=teacher` доступен администратору для выбора учётной записи.

## Frontend и проверки

Рабочий экран `frontend/src/screens/Teachers.tsx` использует общую фирменную тему. Есть список, поиск, фильтр, пагинация, просмотр профиля, создание, изменение, выбор аккаунта, подтверждение архива и восстановление через статус. Выбор аккаунтов проходит все страницы фильтрованного списка пользователей. Руководитель и педагог получают интерфейс чтения; безопасность дополнительно обеспечивается серверными проверками.

Интеграционные тесты с PostgreSQL проверяют реальные HTTP-запросы каждой роли, чужие ID, объединение ролей, блокировку и отзыв сессии, CSRF, поиск на кириллице, буквальные wildcard, пагинацию, nullable PATCH, уникальность связи, архив и сохранение истории. Браузерные проверки используют тестовые ответы только в Playwright и покрывают формы, поиск, просмотр, архив, роли, WCAG A/AA, клавиатуру и ширину 360 px.
