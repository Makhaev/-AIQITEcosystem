В столбце PR/commit это явно обозначено для каждой строки. Снимок исходников
в комплекте передачи имеет файловые SHA-256. Новый отчёт P0/R10 дополнительно
содержит хеши всех Go/SQL/mod/sum файлов до испытания и подтверждает их
неизменность до конца прогона.

Допустимые статусы: «не начато», «в работе», «реализовано — проверка не выполнена»,
«проверено», «принято». «Проверено» здесь означает подтверждённую реализацию
соответствующего требования локальными испытаниями. Удалённый CI, условия
эксплуатации и передача оцениваются отдельно в R11–R14. «Принято» выставляется
только по фактическому решению заказчика. Ни одно требование пока не принято.

## Выполнение шести шагов

1. **P0:** реализован и проверен. Команда `node scripts/verify-p0.mjs` повторяет
   девять тестов прав и два теста R10 на настоящем PostgreSQL. В отчёте есть
   все именованные подслучаи, длительность, среда и хеши исходников. Она не
   принимает пропуски, отсутствие ожидаемого теста или изменение исходников
   во время проверки. Условия и результаты представлены ниже.
2. **P1:** код, SQL, backend, OpenAPI, frontend, тесты и описания R03–R09
   присутствуют; сводка и применимые миграции указаны в строках реестра.
   Сохранён полный успешный прогон 19.10.2026. Повторять его без изменений кода
   ради новой даты не требуется; изменения после фиксации SHA проверяются снова.
3. **Архитектура:** выполнен базовый вариант R10. Повторная проверка переносит
   непустую прежнюю схему в изолированной схеме тестовой БД, сравнивает историю
   и проверяет откат сбоя. Уже работающая локальная БД с миграцией 016 не
   изменяется этим прогоном. Предыдущая миграция рабочей локальной копии с
   предварительным backup описана в [истории R10](completion-progress.md).
4. **Контейнеры/HTTPS/копии:** новый запуск `node scripts/verify-r11.mjs`
   остановился до создания контейнеров из-за отсутствия Docker. Пользователь
   выбрал подготовку Docker Desktop на этом компьютере. После сообщения о
   готовности проверяются Engine/Compose, чистый стенд и HTTPS; затем R12 на
   отдельном защищённом хранилище. Нативный прогон не засчитывается за контейнерный.
5. **Браузер/нагрузка:** настоящий сценарий и нагрузка уже выполнены; ошибки
   ожидания/селектора теста исправлены и E2E повторён на новой БД. Для финального
   результата нагрузка повторяется на той же фиксированной версии приложения
   и согласованных ресурсах. Docker Desktop сам по себе не подтверждает,
   что ОС/БД/приложение укладываются в общий стенд 2 vCPU/4 GB.
6. **CI/передача:** локальный комплект готов, но публикация не разрешена и
   GitHub-параметры не согласованы. Имеющийся CI базового SHA failed на
   `go test -race ./...`; доступная публичная аннотация даёт только exit 1,
   первопричина по ней не установлена. Локальный обычный `go test` не заменяет
   race/удалённый CI. После разрешения нужны реальные Issues/PR, commit,
   успешный CI, решения по замечаниям и приёмка; затем выпуск.

## Демонстрация проверок P0

| Проверяемое свойство | Конкретное доказательство в отчёте P0 |
| --- | --- |
| Педагог получает только id/name/status; смешанная роль учитывается отдельно для каждого ученика | TestCompletionStudentProjectionByObjectAndCombinedRoles |
| Учебные вложения не раскрывают чужих учеников после фиксации состава | TestCompletionNestedStudentVisibilityAndFrozenRoster |

| Отзыв связей и блокировка скрывают объект и отзывают доступ | TestTaskTeacherWithdrawalAndAccountBlocking |
| Во время ожидания блокировки повторно проверяются права ответственного и автора | TestTaskAssignmentConcurrentRevocation, TestTaskAssignmentRechecksAuthorAfterWaiting |
| Сбой audit откатывает изменение задачи | TestTaskAssignmentAuditFailureRollsBack |

Это демонстрация фактических автоматических результатов в отчёте. Живой показ
заказчику, участники и решение о приёмке не выдумываются. Для реального показа
используется [журнал демонстраций](handover-r14.md#демонстрации-и-решения).

Повторение на отдельном тестовом PostgreSQL (не на локальной рабочей БД 55432):

```powershell
$env:STAGE8_TEST_MODE = 'synthetic'
$env:TEST_DATABASE_URL = '<URL отдельного тестового PostgreSQL с btree_gist>'
node scripts/verify-p0.mjs
node scripts/check-execution-report.mjs
```

Нужны Go 1.24+ в PATH (либо `GO_BIN`) и Node 22.12+. Тесты создают случайные
схемы `aiq_test_*` и удаляют их при завершении. Пароль подключения и HTTP-тела
не попадают в отчёт. Скрипт отказывается использовать БД запущенного проекта
на 55432 и URL, совпадающий с `DATABASE_URL`.

## Что необходимо для продолжения

Пользователь подготавливает и запускает Docker Desktop; затем сообщает о
готовности. До запуска нагрузки фиксируются лимиты и размещение БД/приложения.
Отдельно остаются решения владельца по публичному origin и имени
`aiq-platform`, разрешение публикации, GitHub identity/доступ и целевое
эксплуатационное хранилище. Полный список A01–A09 — в [чек-листе](acceptance-r14.md).
Текущее поручение по разделу 8 не отменяет отдельные согласования R14.

Обновление после каждого шага: внести результат и ссылку на доказательство,
при наличии — реальный PR/commit; выполнить проверку реестра, обновить комплект
командой `node scripts/r14-package.mjs`. При невыполненном шаге оставить
соответствующий открытый статус. «Принято» требует отдельного документа с
датой, участниками, проверенным SHA и решением заказчика.
