# Доработки P1: карточки, история и задачи

Реализация R03–R09 из [ТЗ завершения](tz-completion.md). Фактические результаты проверок и оставшиеся P2: [completion-progress.md](completion-progress.md). Все примеры относятся к `/api/v1`; изменяющие запросы требуют сессию, CSRF и разрешённый Origin.

## Родители и Student 360

Перед сохранением родителя форма вызывает административный `POST /parents/contact-matches` с `phone`, `email` и `exclude_id` при редактировании. Телефоны нормализуются, email сравнивается без регистра. Учитываются архивные карточки; текущая карточка исключается. Ответ — обычная страница `items/total/page/page_size`, элементы содержат `id/name/status/matched_fields`, без контактов других родителей.

В URL проверки допустимы только `page` и `page_size`; контакты и исключаемый ID передаются в JSON-теле. По умолчанию возвращаются 20 записей, максимум — 100; в форме есть переход между страницами совпадений. У каждой записи явно показан статус. Совпадение обоих контактов даёт один элемент с двумя `matched_fields`.

Предупреждение позволяет явно подтвердить создание отдельной карточки или сохранение изменений текущей. Изменение введённых данных отменяет подтверждение. Ошибка проверки сохраняет форму, убирает прежние совпадения и возможность подтвердить их, предлагает кнопку «Повторить проверку». Успешная проверка без совпадений продолжает сохранение. Совпадение имени не является дублем; API сохранения допускает общие семейные контакты без отдельного токена подтверждения. Проверка не пишет audit; контакты не попадают в технические логи.

Основной агрегат ученика — `GET /students/{id}/overview?from=YYYY-MM-DD&to=YYYY-MM-DD`. Старый `/360` остаётся эквивалентным alias. Даты включительны по Москве; без параметров сохраняется прежний период последних 30 дней. Полная карточка содержит `age`: полные календарные годы на текущую московскую дату, `null` без даты рождения. Для 29 февраля в невисокосном году день рождения считается 1 марта. В ограниченном ответе педагога ключ `age` отсутствует вместе с другими приватными полями.

## Снимок завершённого занятия

Первое успешное завершение сохраняет название программы, название модуля при наличии, тему и время снимка. API занятия и история посещаемости Student 360 используют эти значения. Переименование справочника их не меняет. Завершение, снимок и audit находятся в одной транзакции; повторное завершение не перезаписывает историю.

`snapshot_state` принимает `not_captured`, `captured`, `legacy_unknown`. Миграция 012 помечает старые завершённые занятия `legacy_unknown`, сохраняет исходные записи и не восстанавливает выдуманные исторические названия. Для них интерфейс явно сообщает, что показаны текущие справочники.

Администратор открывает «Исторический снимок» и вызывает `POST /lessons/{id}/snapshot` с `program_name`, `module_name` (или `null`), `topic`, `reason`. Операция доступна только завершённому занятию. Тема, модуль и группа занятия с историческим снимком (включая `legacy_unknown`) не изменяются обычным PATCH даже после возврата в расписание: сервер возвращает `409 snapshot_correction_required`.

Предыдущая версия остаётся в `lesson_snapshot_versions`; административный `GET /lessons/{id}/snapshot-history` возвращает пагинированный список с ID DESC. Неизвестные значения старой версии остаются `null`. Миграция 013 добавляет причину исправления (`reason`): она сохраняется вместе с версией в закрытой учебной истории и отображается только администратору. У ранее сохранённых версий причина остаётся `null`. Обновление и удаление версий запрещены триггером БД; API таких операций нет. Исправление, предыдущая версия, причина и audit сохраняются в одной транзакции. В audit записываются только названия изменённых полей, без значений и текста причины.

## Перенос с обновлением состава

Обычный PATCH после фиксации журнала допускает изменение времени в пределах текущей московской даты занятия. Для смены даты администратор использует «Перенести с обновлением состава»: выбирает даты, проверяет учеников на новую дату, указывает причину и подтверждает перенос. Изменение начала, окончания, выбранных участников или причины сбрасывает подтверждение. Пока состав загружается или его загрузка завершилась ошибкой, подтвердить перенос нельзя; доступен повтор загрузки.

`POST /lessons/{id}/reschedule` принимает `starts_at`, `ends_at`, полный массив `enrollment_ids` (допустим пустой массив; отсутствие и `null` запрещены) и `reason` длиной 1–1000 символов после удаления крайних пробелов. Доступен только `scheduled`; остальные статусы дают `409`. Зачисления должны принадлежать группе и включать новую московскую дату (обе границы включительны). Состав, даты, запись в `lesson_reschedules` и audit сохраняются атомарно; EXCLUDE-ограничения продолжают защищать от пересечений группы и педагога. Миграция 014 сохраняет причину в истории переноса и запрещает UPDATE/DELETE записей истории. У старых записей причина остаётся `null`; текст причины не записывается в audit.

Отметки оставшихся участников сохраняются. Новые участники получают `unmarked`; исключённые строки остаются с `included=false` и не участвуют в показателях. Повторное включение возвращает прежнюю строку и отметку. После переноса в будущее редактирование посещаемости заблокировано до нового начала. Ошибки конфликта, состава или audit откатывают всю операцию.

## Задачи

Миграция 011 добавляет `closed_at` и триггер переходов. Новая задача создаётся только в `todo`. Статусная операция и PATCH используют одинаковую матрицу:

| Переход | Право |
| --- | --- |
| todo → in_progress; in_progress → done | Ответственный, admin, leader |
| todo / in_progress → cancelled | Постановщик, admin, leader |
| done → in_progress; done → cancelled | Постановщик, admin, leader |

Другие переходы дают `409`; разрешённый переход без соответствующего права — `403`. `cancelled` не открывается. Постановщик с активным аккаунтом и доступом к приложению сохраняет чтение, отмену и возврат после смены роли; это не даёт права редактировать поля, переназначать или читать связанный объект.

При закрытии открытой задачи сервер устанавливает `closed_at`. Между закрытыми статусами дата сохраняется; при повторном открытии очищается, следующее закрытие получает новую. Повтор текущего статуса не изменяет дату и не создаёт критический audit. Старые закрытые задачи имеют `closed_at=null`: интерфейс показывает «Историческая дата закрытия неизвестна».

## Dashboard

Период по умолчанию теперь охватывает весь текущий московский календарный месяц, включая последний день. В SQL используется полуоткрытый интервал от начала месяца до начала следующего. Поля формы показывают реальные границы. Формула посещаемости и независимость текущих количеств от периода сохранены.

Миграции 001–014 применяются автоматически при запуске или отдельной командой migrate. Перед эксплуатационным обновлением требуется резервная копия по [инструкции](operations.md); выполненные локальные проверки миграций не заменяют проверку восстановления, остающуюся в P2.
